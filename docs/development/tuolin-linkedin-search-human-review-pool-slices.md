## 1. 交付原则

每个 AFK 切片必须交付一条可运行、可持久化、可观察并可自动验证的端到端路径。不得只修改访谈文案、Excel 格式、某个状态字段或单个测试夹具。源码、插件镜像、自然语言输出、运行状态、账本、工作簿和测试必须保持一致。

- **AFK**：使用确定性浏览器观察、临时工作区和真实 `.xlsx` 文件即可完成实现与自动验证。
- **HITL**：必须在老板电脑的官方 Codex Chrome、已登录 LinkedIn 和人工审核环境中完成。
- 搜索、推理、工作簿同步和人工审核不构成发送授权。
- S15 只能对 S14 后生成并重新打印的精确最终发送快照获得授权，当前开发授权不能替代该门禁。
- 老版本运行保持原 schema；新实现不得静默迁移或重新解释旧运行。

## 4. 详细切片

### S01 — 建立新版访谈与运行简报

**类型：** AFK
**Blocked by：** None - can start immediately
**用户故事：** 3–8、101–103、117–119

#### What to build

从自然语言任务创建到已确认简报交付新 schema 的完整路径。保留组合关键词、Posts 排序、发布日期、留言选择和固定发送间隔，将“最多邀请人数”替换为“本次最多找多少个联系人给您筛选？”。默认审核池为 50，允许 1–100；默认间隔为 2 分钟，允许不低于 1 分钟的整数分钟。

#### Acceptance criteria

- [ ] 新运行使用显式新 schema，旧运行不会被静默迁移。
- [ ] 访谈仍逐题询问，只问缺失的可执行字段，题号稳定且不重复保存同一答案。
- [ ] 审核人数问题使用老板可理解的中文措辞，默认 50，接受 1 和 100，拒绝 0、101 和非整数。
- [ ] 不再预先询问或持久化固定每轮 10 人的邀请上限。
- [ ] 间隔推荐 2 分钟，接受 1 分钟及更大的整数分钟，拒绝小于 1 分钟或非整分钟。
- [ ] 组合关键词保持完整、有序、大小写不敏感去重，并独立搜索。
- [ ] 运行简报、change log、自然语言输出和恢复状态使用同一字段语义。

### S02 — 解除搜索与邀请额度的前置绑定

**类型：** AFK
**Blocked by：** S01
**用户故事：** 11–16、30–37

#### What to build

账号绑定后只记录滚动 168 小时容量作为信息，不再用它缩小人工审核池或阻止发现。容量为 0 时仍可进入 Posts 搜索、初筛、工作簿和人工审核，只有 Connect 阶段被阻断。

#### Acceptance criteria

- [ ] 账号绑定在容量 0、部分容量和完整容量下都能进入搜索。
- [ ] 发现停止条件不读取邀请容量或历史固定 10 人上限。
- [ ] 容量证据仍持久化，供最终选择后重新计算。
- [ ] 旧 schema 进入不兼容转换时明确要求新建任务，而不是改写旧状态。
- [ ] 自然语言明确区分“可以继续找人”和“当前不能发送邀请”。

### S03 — 实现宽进严出的贴文初筛

**类型：** AFK
**Blocked by：** S02
**用户故事：** 38–53

#### What to build

从一条可见 LinkedIn 贴文贯穿初步判断、候选持久化和 Codex 审核输出。只硬排除明显语义误命中、同类或同基础材料直接制造商/供应商、重复或已联系成员，以及没有普通 Connect 路径的成员。其余业务上可能相关但证据不足的联系人进入人工审核。

#### Acceptance criteria

- [ ] 每个进入审核池的对象都有完整贴文、关键词、作者、公司、角色、Connect 证据和可追溯 URL。
- [ ] 初步判断输出可能的商业角色、支持证据、关键疑点和保留/排除建议。
- [ ] 不输出伪精确相关性分数，不把候选称为已确认买家或客户。
- [ ] 安装商、承包商、集成商、制品商、设备商、项目运营方、品牌商、经销商、零售商和贴牌方可在不确定时进入人工审核。
- [ ] 六类真实测试样例覆盖直接供应商、安装商、语义误命中、隔热制品商、软件术语和同材料销售人员。

### S04 — 实现一家公司一名候选联系人

**类型：** AFK
**Blocked by：** S03
**用户故事：** 54–62

#### What to build

将相关公司解析为一名可行动联系人，依次优先 Owner/Founder、Procurement/Purchasing/Sourcing、Managing Director/General Manager、Product Manager；必要时允许另一名可见业务相关负责人，但必须记录角色与业务的选择理由。

#### Acceptance criteria

- [ ] 每家公司同时最多占用一个审核池位置。
- [ ] 优先联系人没有普通 Connect 时会继续尝试下一优先级。
- [ ] 后备负责人只有在存在可见职责证据和明确选择理由时才可入池。
- [ ] 同公司重复成员不会同时形成候选或绕过去重。
- [ ] 找不到可验证个人和 Connect 路径时生成 Unresolved Relevant Lead，不占审核池位置。

### S05 — 生成账号级累计潜客 Excel

**类型：** AFK
**Blocked by：** S04
**用户故事：** 63–82

#### What to build

为每个标准化 LinkedIn 账号 profile URL 创建一份累计 `.xlsx`。工作簿提供“潜客联系人”“潜客证据”“发送记录”三个稳定工作表。运行状态仍是执行真相，Excel 是老板审核和累计业务记录投影。

#### Acceptance criteria

- [ ] 同一账号的标准化 URL 始终定位到同一工作簿，不同账号永不共用。
- [ ] 联系人表一人一行，包含身份、公司、连接状态、首次/最近发现、老板判断和老板备注。
- [ ] 老板判断配置为仅允许“发送、排除、待定”的 Excel 下拉列表，新联系人默认“待定”。
- [ ] 证据表逐条保存完整贴文、URL、关键词、运行、Codex 判断、证据和疑点。
- [ ] 发送记录表保存不可变批次成员、留言、间隔、时间、尝试和结果。
- [ ] 使用原子替换并保留可恢复前一版本；损坏或锁定时响亮失败且不破坏最后好版本。
- [ ] 真实 `.xlsx` 被独立读取器关闭后重开，仍能验证工作表、完整正文和下拉验证。
- [ ] 每次同步在运行目录生成含修订号、行 ID 和摘要的 receipt。

### S06 — 实现跨任务去重与累计更新

**类型：** AFK
**Blocked by：** S05
**用户故事：** 83–93

#### What to build

把共享账本、账号工作簿和运行候选状态协调成跨任务去重路径。重复成员更新同一联系人行并追加新贴文证据，但不占当前运行“新联系人”名额。

#### Acceptance criteria

- [ ] 成员身份以标准化 profile URL 为主键，显示名不参与身份判断。
- [ ] 重复成员新贴文追加证据并更新最近发现，不新增联系人行。
- [ ] 已发送、邀请 Pending、已连接和老板排除的联系人不会重新进入新审核池。
- [ ] 排除联系人只有在老板改回待定后才可再次考虑。
- [ ] 历史待定联系人保留，可被当前任务明确选中，但不自动加入且不算新发现。
- [ ] 重复公司不同成员遵守一家公司一人的当前机会边界。
- [ ] 工作簿和账本冲突时停止并给出协调错误，不把 Excel 当并发锁。

### S07 — 按人工审核人数持续滚动搜索

**类型：** AFK
**Blocked by：** S06
**用户故事：** 1–8、26–37、85

#### What to build

把发现完成条件改为成功持久化并同步到工作簿的 New Review Contact 数量。取消每个关键词最多检查 50 条贴文的硬停止，保留三次连续到底、等待且无新增唯一贴文身份的可验证耗尽规则。

#### Acceptance criteria

- [ ] 目标 50 时不会因为只检查了 50 条原始贴文或产生少量候选而停止。
- [ ] 只有新建候选卡和工作簿同步都成功后才增加审核池计数。
- [ ] 重复成员、广告、placeholder、重复贴文和 unresolved lead 不增加计数。
- [ ] 一次或两次无增长不耗尽，第三次才耗尽；任何新唯一贴文都会重置计数。
- [ ] 到达目标立即停止；全部关键词验证耗尽时允许以实际人数完成。
- [ ] 每次滚动证据和恢复位置持久化，中断后不会从头重复计数。

### S08 — 实现组合关键词均衡采样

**类型：** AFK
**Blocked by：** S07
**用户故事：** 17–29、36–37

#### What to build

按审核池人数和关键词数量确定首轮软份额，余数按输入顺序分配。每个关键词获得首轮机会；份额未完成但已耗尽时将空间释放。首轮结束后按原顺序重访仍能产出候选的关键词，直到目标满足或全部耗尽。

#### Acceptance criteria

- [ ] 软份额总和等于审核池目标，计算和余数分配完全确定。
- [ ] 宽泛首词不能在其他词获得首轮机会前独占整个池。
- [ ] 耗尽词的未使用份额不会阻止其他词继续贡献。
- [ ] refill 只在所有未耗尽词获得首轮机会后开始，并保持原始关键词顺序。
- [ ] 不自动扩词、翻译关键词或放宽排序、日期和 Connect 门禁。
- [ ] 每个关键词保存目标、贡献数、首轮状态、耗尽证据和 refill 资格，可确定性恢复。

### S09 — 从累计表形成老板审核结果

**类型：** AFK
**Blocked by：** S06、S08
**用户故事：** 72–75、87–95

#### What to build

读取累计表中的“发送、排除、待定”和老板备注，生成本次明确选择。允许本轮新增联系人和老板本次明确选择的历史待定联系人进入当前发送选择；任何历史联系人都不得因旧状态自动发送。

#### Acceptance criteria

- [ ] Codex 搜索总结显示新增、重复、硬排除、unresolved、关键词贡献和工作簿修订。
- [ ] 老板可在 Excel 中筛选，不要求在聊天中阅读 50 张完整卡片。
- [ ] 发送、排除、待定和老板备注被读取并产生可审计反馈记录。
- [ ] 历史待定仅在本次明确选择后进入发送准备，所有历史对象重新校验。
- [ ] 排除和已联系状态不会进入当前选择。
- [ ] 选中行在进入下一阶段前绑定完整证据引用。

### S10 — 生成不可变的最终发送快照

**类型：** AFK
**Blocked by：** S09
**用户故事：** 9–16、94–100

#### What to build

将老板本次精确选择冻结为 Final Dispatch Snapshot，并在 Codex 中重新打印每名联系人、完整来源贴文和 Codex 判断。批准人数由选择数量决定，不再固定为 10。快照创建前重新计算滚动容量和实时资格。

#### Acceptance criteria

- [ ] 快照冻结账号、成员、公司、证据摘要、完整贴文引用、留言、间隔、批准人数、有效人数和容量证据。
- [ ] 老板选择 12 人且容量足够时可形成 12 人授权批次。
- [ ] 容量为 0 时只阻止 Connect，不删除选择、工作簿或审核结果。
- [ ] 容量小于选择数量时返回冲突，绝不自动取前 N 人；老板必须重新选择并确认精确子集。
- [ ] 快照创建后的工作簿修改不能改变待授权成员或批次参数。
- [ ] 未确认精确快照时不能开始任何外部邀请。

### S11 — 执行可恢复的间隔发送

**类型：** AFK
**Blocked by：** S10
**用户故事：** 101–107

#### What to build

在新快照和新 schema 上复用现有逐人预检、点击、可见结果、账本记账、局部失败、平台停止与恢复合同。按快照冻结的整数分钟间隔顺序发送，并同步工作簿发送历史。

#### Acceptance criteria

- [ ] 1 分钟、2 分钟和更大整数分钟均可冻结并执行；小于 1 分钟被拒绝。
- [ ] 每名联系人点击前重新校验账号、身份、Connect、实时状态、账本、容量、留言和时间门禁。
- [ ] 只有可见发送成功或变为 Pending 才写成功账本。
- [ ] 每次授权、尝试、成功、失败和停止都追加到工作簿发送记录且不覆盖历史。
- [ ] 普通中断可对账后重新授权剩余同一快照；平台限制、CAPTCHA、登录失效或账号变化立即停止。
- [ ] 恢复时保留剩余时间门禁，不缩短已授权间隔。

### S12 — 把老板反馈转为可确认的筛选规则

**类型：** AFK
**Blocked by：** S09
**用户故事：** 108–116

#### What to build

将每次老板判断和备注保存为有来源的 review feedback。后续 Codex 判断可以引用相关历史，但不能从少量决策静默生成硬规则。提供规则提案、支持例、冲突例和明确确认后的版本化规则投影。

#### Acceptance criteria

- [ ] 老板备注被视为强显式证据；无备注判断只能形成标记为弱推断的上下文。
- [ ] 后续判断引用具体历史反馈 ID，不用“系统已学习”替代证据。
- [ ] 重复保留、排除和矛盾模式可以生成规则提案，但默认不激活。
- [ ] 提案同时展示支持和冲突案例。
- [ ] 只有老板明确确认后规则才可成为未来硬行为，并保存措辞、范围、版本、确认时间和证据引用。
- [ ] 规则撤销或版本变化可追溯，不重写历史判断。

### S13 — 完成源代码、插件镜像与回归验证

**类型：** AFK
**Blocked by：** S11、S12
**用户故事：** 117–120

#### What to build

同步源码与 `plugins/tuolin-marketplace` 镜像，更新 Skill、agent UI 元数据、版本、安装检查和远程验收文档。完成全量自动回归、Skill 校验、插件校验、镜像校验和可安装包检查。

#### Acceptance criteria

- [ ] 所有 LinkedIn search 运行模块、入口脚本、Skill 和 agent 元数据在源码与插件镜像中保持字节一致。
- [ ] 新版本安装检查无需本地知识库即可通过。
- [ ] 旧 schema 测试和新 schema 测试边界明确，没有静默兼容。
- [ ] Excel、平衡采样、去重、快照、容量、间隔、反馈和恢复测试全部通过。
- [ ] Skill `quick_validate.py`、插件 `validate_plugin.py`、包解压检查和项目全量测试通过。
- [ ] 使用官方 cachebuster 更新流程，不手工修改 marketplace 配置。

### S14 — 老板电脑只读业务验收

**类型：** HITL
**Blocked by：** S13
**用户故事：** 1–100

#### What to build

在老板电脑安装新版插件，新开 Codex 会话，使用官方 Codex Chrome 和已登录 LinkedIn 账号执行真实关键词任务。目标为约 50 名人工审核联系人，完成持续滚动、判断、工作簿同步和老板筛选，全程不发送连接邀请。

#### Acceptance criteria

- [ ] 无本地知识库也能创建任务、完成访谈并绑定正确账号。
- [ ] 每个组合关键词获得首轮搜索机会，页面继续滚动到池满或可验证耗尽。
- [ ] 工作簿包含可供老板判断的完整贴文证据和 Codex 推理，不把低置信对象伪装为买家。
- [ ] 重复联系人和历史状态正确累计，不重复占用审核池。
- [ ] 老板可使用下拉框和备注完成筛选。
- [ ] 整个验收不点击或提交 Connect。

### S15 — 老板电脑真实邀请验收

**类型：** HITL
**Blocked by：** S14
**用户故事：** 94–107

#### What to build

读取老板完成的审核选择，重新校验真实容量和 LinkedIn 状态，生成并在 Codex 中打印精确最终发送快照。获得该快照的外部动作授权后，执行一个受控真实批次，验证间隔、结果、账本、Excel 和恢复状态一致。

#### Acceptance criteria

- [ ] 授权前完整打印账号、精确联系人、来源证据、留言、间隔、容量和快照摘要。
- [ ] 容量不足时由老板重新选择精确子集，不自动截断。
- [ ] 未获得当前快照确认时不发送任何邀请。
- [ ] 获得授权后按冻结顺序和间隔发送，不逐人重复询问。
- [ ] 真实成功、失败或平台停止在 Codex、运行状态、共享账本和工作簿中一致。
- [ ] 验收结论明确区分通过、部分通过、blocked 和未执行。

## 5. 完成定义

- S01–S13 只有在各自自动化验收标准通过后才可标记完成。
- S14、S15 不得使用模拟浏览器结果冒充真实验收。
- S14、S15 的未执行不影响说明 AFK 开发已完成，但可安装版本不得被描述为已经通过真实业务验收。
- 每个切片完成时记录改动文件、验证命令、结果和剩余风险。
- 最终交付必须同时给出本地开发文档、PRD、可安装插件版本、测试结果和老板电脑下一条自然语言验收指令。
